## 1. Why an SOP

A chain is data (`N2`), so its lifecycle differs from code's: **written once, reused for a long time, referenced from several places, edited by a non-developer (an LLM)**. That raises four problems that must be solved:

| Problem | This design's answer |
|---|---|
| Where a chain is stored and how it is fetched | the `TemplateStore` abstraction + two kernel implementations (file / SQLite); a host may plug in MySQL itself |
| How a change leaves a trace | one row per chain, **updated in place**, plus `template_audit` keeping only **fingerprints**, retained forever (§2, §3) |
| How a bad chain is kept out | `publish` is the **only write entry point**, and before writing it forces a `lint` plus a run of the snapshots that already exist (§6) |
| How an LLM edits by the rules | the step-by-step `S0–S7` SOP + deterministic error codes + structured query commands (§7, §8) |

**Invariants (storage layer)**:

- **One row per chain**: `(root_domain, tpl_key)` is unique; changing a chain = an in-place `UPDATE`, with no version rows and no pinning (draft `01` Q1').
- **A single write entry point**: no method other than `publish` can modify a `template` row.
- **Audit is immutable**: `template_audit` is append-only, and its rows are never modified or deleted (draft `01` Q18).
- **Anything read back must be recompiled**: the `graph` in a `Store` is **data**, not a compilation product; every read-back goes through `compile()`, and a trusted compilation product is never deserialized (`01` §8).

## 2. Data model: `Template`

| Column | Type | Constraint | Meaning |
|---|---|---|---|
| `chain_id` | `str` | PK | `uuid4().hex` (32 characters, no dashes). Generation is confined to **one pure function**, `new_chain_id()`, so switching to ULID later touches a single place |
| `root_domain` | `str` | NOT NULL | site identity (e.g. `ah.gov.cn`); `local` is fine for local practice |
| `tpl_key` | `str` | NOT NULL | human-readable business name (e.g. `\u653f\u5e9c\u6587\u4ef6\u5217\u8868` / `\u6b63\u6587\u8be6\u60c5`); unique within a domain |
| `status` | `str` | NOT NULL, default `draft` | `draft` / `ready` / `disabled`; `disabled` is set by hand only |
| `source` | `str` | NOT NULL, default `agent` | a three-value enum: `human` (written by a person) / `agent` (generated by AI) / `import` (bulk import or migration) |
| `graph` | JSON | NOT NULL | the chain data of `03` §2 |
| `create_time` | `str` | NOT NULL | ISO 8601 (UTC, with `+00:00`) |
| `update_time` | `str` | NOT NULL | as above; refreshed by every `publish` |

**Indexes**: PK `(chain_id)` · `UNIQUE(root_domain, tpl_key)` · `idx(root_domain)` · `idx(status)`.

The character-set constraint on `tpl_key` (lint `UP2-E3002`): `^[\w\u4e00-\u9fff][\w\u4e00-\u9fff.-]{0,63}$` — letters, digits, underscores, Chinese characters, dots and hyphens, and it may not start with a dot or a hyphen.

> **Why constrain the character set**: `FileStore` uses `tpl_key` as a file name (Windows forbids `\ / : * ? " < > |`); putting the constraint in the lint layer keeps the behaviour of both Stores identical, and it also disposes of the special rule from draft `01` R2 ("`tpl_key` must not start with `:`") — a `:` simply does not make it into the character set.

### 2.1 `TemplateAudit`

| Column | Meaning |
|---|---|
| `seq` | auto-increment sequence (the audit order within one `chain_id`) |
| `chain_id` | points at `Template.chain_id` |
| `at` | the moment of the change (ISO 8601 UTC) |
| `actor` | who changed it: a **free-form string** passed in by the caller (e.g. `llm:claude`, `ops:zhang`); `unknown` when it is not supplied |
| `source` | the category of change: `human` / `agent` / `import` |
| `old_hash` | the `graph` fingerprint before the change; `null` on first creation |
| `new_hash` | the `graph` fingerprint after the change |
| `note` | a remark (optional; required when `--skip-tests` is used, see §6) |

**Only fingerprints are stored, never the full `graph`**: a change is an in-place update, and the hash records "what changed"; rollback goes through a backup (§10). This judgement from draft `01` Q18 holds — chains change rarely, and full history is not worth the storage and consistency cost.

**Where `actor` comes from (settling the open item of draft `01` §6-f)**: `publish(..., actor: str, source: Source)` takes it explicitly from the caller; the kernel does not guess. The CLI uses `--actor` / `--source`, defaulting to `unknown` / `agent`. The reason: the kernel cannot reliably infer "who", and any automatic inference (process name, environment variable) is distorted inside batch scripts.

## 3. Fingerprints

```python
def graph_hash(graph: Mapping[str, Any]) -> str:
    blob = json.dumps(graph, sort_keys=True, separators=(",", ":"), ensure_ascii=False,
                      allow_nan=False)
    return hashlib.blake2s(blob.encode("utf-8"), digest_size=16).hexdigest()   # 32 hex
```

| Rule | Content |
|---|---|
| Canonicalisation | `sort_keys=True` (key order is irrelevant), `separators=(",", ":")` (whitespace is irrelevant), `ensure_ascii=False` (Chinese is kept as is), `allow_nan=False` (a graph JSON cannot express is refused with `UP2-E1004` **before** anything is written) |
| Algorithm | `blake2s`, `digest_size=16` |
| Fingerprint scope | **only `graph` is hashed**; `status` / `source` do not enter the fingerprint (a status change must not produce an audit row saying "the chain changed") |
| Idempotence | the same `graph` yields the same fingerprint whether it comes in from a JSON file or from a dict |
| Use | audit trail, and the no-op decision of `publish` (the same hash writes no audit row) |

> **`dsl_version` was deleted** (see `D-04-3`): the dialect of the stored JSON is checked by the **compiler**, not by a stored number — a pre-0.7 chain carries `steps` instead of `nodes` and fails L1 lint with a definite code — so a hand-bumped generation number earned nothing and was one more thing to forget. "When did this row change, and to what" is answered by `update_time` plus the audit fingerprint.

## 4. The `TemplateStore` protocol

```python
class TemplateStore(Protocol):
    def get(self, root_domain: str, tpl_key: str) -> Template | None: ...
    def list(self, *, root_domain: str | None = None,
             status: Status | None = None) -> list[TemplateMeta]: ...
    def publish(self, graph: Graph, *, root_domain: str, tpl_key: str,
                actor: str, source: Source, note: str | None = None) -> PublishResult: ...
    def audit(self, chain_id: str) -> list[AuditRow]: ...
```

| Method | Contract |
|---|---|
| `get` | returns the complete `Template` (including `graph`) or `None`; **performs no `compile()`** (compiling is the caller's business; the Store holds no engine state) |
| `list` | returns **metadata** (without `graph`), for listings and gate scans |
| `publish` | the **only write entry point**; atomic; returns `PublishResult(chain_id, old_hash, new_hash, changed, audit_seq)` |
| `audit` | returns audit rows in ascending `seq` order |

**Implemented**: `audit_seq` is the store's own sequence number; the file Store numbers the lines of
one chain's audit file (so it restarts at 1 for every chain) while SQLite's
`INTEGER PRIMARY KEY AUTOINCREMENT` numbers the whole table. Only the **order within one chain** is
promised — a caller must not compare `seq` across chains or across stores.

**Implemented**: `get` answers parsed JSON data, and the **callers** compile it: `publish` recompiles
the row it read before trusting it (§5 step 3), and `up2 get` compiles the graph before printing it,
so a hand-edited stored chain is reported by the compiler instead of being served as valid. `up2 get`
prints the row **with its fingerprint**; `--graph` prints only the chain data, which is the backup
material of S7.

**Interface design constraint** (`Protocol` rather than a base class: cross-module injection, no reverse dependencies, see `~/.dsh/AGENTS.md` §5): the kernel imports no concrete Store; `cli` picks the implementation from configuration.

### 4.1 `FileStore` (the default)

```
$UP2_HOME/                     # default ~/.uniparser2; an environment variable can override it
  chains/
    <root_domain>/
      <tpl_key>.json           # one row = one file (the complete JSON of a Template)
  audit/
    <root_domain>/
      <tpl_key>.jsonl          # append-only, one audit row per line
  samples/
    <root_domain>/<tpl_key>/
      <case>/input.txt         # sample input
      <case>/expected.json     # expected product (snapshot)
```

| Feature | Description |
|---|---|
| Applicability | local development, the trial UI, a single-machine SOP flow |
| Atomic write | write a temporary file → `os.replace()` (an atomic replacement within the same directory) |
| Strict JSON | every row and audit line is written with `allow_nan=False` and read with `parse_constant` rejected; a file that is not strict JSON is reported with `UP2-E1004` and its path, never as a decoder traceback (the same rule covers `expected.json` snapshots) |
| Concurrency | no cross-process lock; the **single-writer assumption** is stated explicitly in the documentation (use SQLite for multiple writers) |
| Version-control friendly | one file per chain, with canonical key order, so `git diff` is readable |

**Implemented — configuration**: `UP2_HOME` (default `~/.uniparser2`) is the store's root, and
`UP2_STORE` (`file` | `sqlite`, default `file`) picks the implementation the CLI opens (`04` §4 says
"cli picks the implementation from configuration" without naming it; a flag on three commands would be
a fourth spelling of the same fact).

**Implemented — how `audit(chain_id)` finds its file**: the layout is keyed by
`(root_domain, tpl_key)` while the method is keyed by `chain_id`, and §2.1's audit row carries no
domain or key column. The file Store therefore scans `audit/**/*.jsonl` and filters by `chain_id`,
which keeps the designed layout and row shape and keeps an audit row reachable after its template row
is gone (the reason §4.2 refuses a foreign key). The cost is proportional to the number of audit rows,
which the applicability above tolerates; a host that outgrows it implements `TemplateStore`.

**Implemented — `samples/`**: the runner that reads this layout is `cli/samples.py`, driven by
`up2 snapshot` (§7-S4) and `up2 test` (§7-S5). The root is `--tests-root` (default `samples`, the
repository's own directory per `05` §3), so `$UP2_HOME/samples/` is the "temporary samples that are
not ready to be committed" of `05` §3 and `<repo>/samples/` the committed contract. A **case** is a
directory carrying `input.txt`; `up2 snapshot --accept` writes its `expected.json`, and a case that
carries an input but no snapshot is a **failure** of G2 rather than a silent pass, because "every
case under `samples/` for this `tpl_key`" is what the gate promises.

### 4.2 `SqliteStore`

```sql
CREATE TABLE template (
  chain_id     TEXT PRIMARY KEY,
  root_domain  TEXT NOT NULL,
  tpl_key      TEXT NOT NULL,
  status       TEXT NOT NULL DEFAULT 'draft',
  source       TEXT NOT NULL DEFAULT 'agent',
  graph        TEXT NOT NULL,
  create_time  TEXT NOT NULL,
  update_time  TEXT NOT NULL,
  UNIQUE(root_domain, tpl_key)
);
CREATE INDEX idx_template_domain ON template(root_domain);
CREATE INDEX idx_template_status ON template(status);

CREATE TABLE template_audit (
  seq        INTEGER PRIMARY KEY AUTOINCREMENT,
  chain_id   TEXT NOT NULL,
  at         TEXT NOT NULL,
  actor      TEXT NOT NULL,
  source     TEXT NOT NULL,
  old_hash   TEXT,
  new_hash   TEXT NOT NULL,
  note       TEXT
);
CREATE INDEX idx_audit_chain ON template_audit(chain_id, seq);
```

- `PRAGMA journal_mode=WAL` (friendly to concurrent readers); **no foreign keys** (an audit row must be able to keep existing after its `template` row is deleted).
- Applicability: multiple writers, SQL queries / gate scans, sharing a database with the host.
- **MySQL is not implemented in this project**: the `template` table of draft `01` is meant for a production database; a host simply implements `TemplateStore`, and this design only guarantees **consistent column semantics** (the column names and constraints of §2 are the vocabulary a host aligns to).

**Implemented**: the database is `$UP2_HOME/store.sqlite3` (this section names no path; a fixed one
keeps the two stores symmetric), and the schema above is created idempotently on the first operation,
never in the constructor — a store object holds no open handle and touches nothing until it is used.
The statements are the ones above with `IF NOT EXISTS`, so the column list, the unique constraint and
the three indexes are exactly this section's.

## 5. Atomicity of writes

The fixed steps of `publish` (with identical semantics in both Stores):

```
1. Validate the tpl_key character set and that root_domain is non-empty  → failure UP2-E3002
2. compile(graph)                                → on failure reject outright (a bad chain cannot get in)
3. Read the old row:
   ├─ absent  → changed = True, old_hash = None
   └─ present → new_hash == old_hash ? → changed = False, **return immediately, write no row at all**
4. Write the template row (INSERT or an in-place UPDATE; update_time refreshed)
5. Append one template_audit row
6. Commit (SQLite: a single transaction BEGIN IMMEDIATE…COMMIT; file: write the chains temporary file first → commit → append the audit row)
7. Read the row back and compare its fingerprint with new_hash  → mismatch is UP2-E3001
```

| Guarantee | Implementation |
|---|---|
| "A bad chain cannot enter the store" | step 2 fails and the whole write is rejected; **an already existing chain is recompiled too** (so a read-back path cannot be bypassed) |
| "Resending the same chain produces no noise" | the no-op decision of step 3 |
| "There is never a chain without an audit row, nor an audit row without a chain" | SQLite uses a single transaction; the file Store lands `chains` first and appends `audit` afterwards (if the second step crashes, "a chain without an audit row" appears, which `up2 doctor` detects and reports as `UP2-E3003`) |
| "Concurrent writes to the same chain" | SQLite: `BEGIN IMMEDIATE` + `UNIQUE(root_domain, tpl_key)`; file: the single-writer assumption |
| "What was written is what was meant" | step 7 |

**Implemented — step 7**: §5.1 defines `UP2-E3001` as "the `graph` **written** under the same
`(root_domain, tpl_key)` does not match the expected fingerprint" and its fix names a concurrent
writer, so the code is a **read-back verification after the write**, not a second read before it. It
catches both a write that silently did not land and a second writer that replaced the row.

**Implemented — failure reporting**: any failure to reach the store (a read in step 3, a write in
step 4, the verification read in step 7) is `UP2-E3004` carrying the underlying exception and the
path, and a failure in step 5 leaves the chain file in place — that is the crash window this section
describes, and `inconsistencies()` reports it. A lost audit row for a chain that **already had one**
is not detectable: audit rows hold fingerprints only (§2.1), so "the row did not change" and "the
audit line was lost" look the same.

> **Origin**: the "transactional rule injection" of the old v3 (`essence` §A10: add first and validate afterwards, rolling back and re-raising on failure). This design moves validation ahead of the write (`N3`, a compile-time failure), leaving the transaction responsible only for the consistency of "chain + audit".

### 5.1 Storage-layer error codes (`UP2-E3xxx`)

| Code | Trigger | Fix hint |
|---|---|---|
| `UP2-E3001` | fingerprint conflict: the `graph` written under the same `(root_domain, tpl_key)` does not match the expected fingerprint | run `up2 get` again and compare; make sure there is no concurrent writer |
| `UP2-E3002` | the `tpl_key` character set is illegal, or `root_domain` is empty | report the character-set regex and the actual value |
| `UP2-E3003` | chain and audit are inconsistent (a chain without an audit row / an audit row without a chain) | `up2 doctor --fix` (which writes the missing audit row; re-publishing is the other remedy) |
| `UP2-E3004` | the Store write failed (permissions / disk / SQLite lock / a missing directory) | report the path and the underlying error |
| `UP2-E3005` | the `publish` gate did not pass (the G2 snapshot regression failed, or `--skip-tests` came without `--note`) | run `up2 test` or supply `--note` |

**Implemented**: the five codes are declared in `core/errors.py` with exactly these triggers, and
both `UP2-E3005` branches are now reachable: `--skip-tests` without `--note` is refused by
`store/gates.py`, and a failed regression by the runner. `UP2-E3004` is raised for a **read** that
cannot reach the store as well as for a write, and the `UP2-E3003` diagnostic carries the
`chain_id` a finding is about, so `up2 doctor --fix` knows which row to repair without parsing the
message.

## 6. The gates on `publish`

`publish` is not merely writing a file; it is a **quality gate**:

| Gate | Default | Skippable |
|---|---|---|
| G1 `lint` (every rule of `03` §10) | mandatory | no — not skippable (`N3`) |
| G2 **regression of the snapshots that already exist** (every case under `samples/` for this `tpl_key`) | mandatory | yes — `--skip-tests`, but then `--note` **must** be given as well, and the audit row records the `note` |
| G3 overwrite prompt | if the old row has `status = "ready"`, `--confirm-overwrite` is required | no |

The design intent of `--skip-tests`: it allows the realistic case of "store the chain first, the samples are not ready yet", but **a trace must be left** — that is the cost of "the audit can answer 'who bypassed the tests, and when'".

**Implemented**: G1 is the store's own `compile` of step 2, so no flag can skip it. G2/G3 are checked
by the CLI before it calls the store, so a refusal writes nothing: `--skip-tests` without `--note` is
`UP2-E3005`, a failed regression is the same `UP2-E3005` carrying the JSON Pointer difference, and a
`ready` row needs `--confirm-overwrite`. G2 regresses the cases of the key the publish names, rooted
at `--tests-root` (default `samples`); a key with **no** case at all is green, which is what keeps
"store the chain first, the samples are not ready yet" workable through `--skip-tests --note`, and a
case that carries an input but no `expected.json` is red rather than silently absent. One edge of
this section is not what the table implies: an unconfirmed overwrite exits `2` as a **usage** error,
because §5.1 assigns that refusal no code and minting one would have taken a number this design
reserved for something else.

## 7. The SOP (an LLM and a person both follow it)

> **The SOP's acceptance standard**: every step has a **mechanically executable acceptance command** and does not depend on human judgement; every failure has a definite next step. This is the concrete shape of "LLM-friendly persistence of frozen parse chains" (goal 2).

### S0 · Preparation

| Item | Requirement |
|---|---|
| `root_domain` | site identity; use `local` for practice |
| `tpl_key` | human-readable business name; matches `^[\w\u4e00-\u9fff][\w\u4e00-\u9fff.-]{0,63}$` |
| Product target | confirm each `["type", name]` stage (a host-registered type, or a built-in one; `03` §3) and the node the run names (the first node is the tool default) |
| Sample input | **at least 1 real input**, placed at `samples/<root_domain>/<tpl_key>/<case>/input.txt` |

**Acceptance**: `up2 ops` can list the available operators and actions (read it before drafting; do not write action names from memory).

```bash
up2 ops --json      # operators / actions / arity and slot roles / argument schema / dependency availability
```

> **Corrected**: the earlier draft wrote `up2 lint --ops` and a `up2 schemas --json` command. There is
> no `--ops` flag on `lint` (`up2 ops` is its own command, and `lint` takes a chain file), and there
> is no `schemas` command: the registered *type* names are the `type` a chain tail declares (`03` §3), and
> `up2 ops` is the single capability self-description of `08` §1.

### S1 · Drafting

The LLM (or a person) produces the chain JSON, **using only operators and actions that appear in `ops.json`**. While drafting, these must be decided explicitly:

1. what the run's input is (the **node's `$in`**; there is no `seed` and no input field, `03` §2) and that materialization is on demand (`03` §6);
2. whether per-item parsing is needed (an `each` stage inside the chain that holds the list);
3. each `["type", name]` stage (`03` §3) and the node the run names (the first node is the tool default);
4. how a value that may be absent is handled: a field whose chain ends in a miss is simply **absent** from the product (`01` §4.2), so a fallback is written at the action level (`py.or`), not configured for the whole run.

**Acceptance**: a parsable JSON file is produced.

### S2 · Static validation

```bash
up2 lint chain.json --json
```

**Acceptance**: `errors == 0`. On failure, fix by error code: each problem carries `code` / `pointer` / `message` / `fix` / `allowed` (the enumeration of allowed values). It is **forbidden** to bypass lint by "running it until it passes".

### S3 · In-place trial (no store write, no network)

```bash
up2 trial chain.json --input text=@samples/<domain>/<tpl_key>/<case>/input.txt --json
up2 trial chain.json --input text=@… --trace --json    # the per-stage trace (06 §5.1)
```

**Acceptance**: the product matches expectations.

**S3 is the only step in the SOP that needs a person (or the semantic judgement of an LLM)** — a chain that runs is not a chain that extracted the right content.

> **Corrected again** (change `add-story-trace`): the earlier note said `--trace` "does not exist",
> and that was true when it was written. It exists now: `up2 trial --trace` prints the run's
> `TraceEvent`s in evaluation order, as one JSON document with `--json` and one line per event
> without it, and the events are the trial bench's own data structure (`06` §5.1), so the CLI and
> the UI cannot disagree. A story file is accepted too: it is run with the story layer, and a host
> function the story calls must be supplied by the CLI, so a missing one is reported with
> `UP2-E1010` before evaluation — the trace then carries the events up to that failure. A query that
> matched nothing is an ordinary `{"state": "ok"}` result carrying the shape's empty value.

### S4 · Freezing the snapshot

```bash
up2 snapshot chain.json --domain <domain> --key <tpl_key> --case <case> --accept
```

**Acceptance**: `<tests-root>/<domain>/<tpl_key>/<case>/expected.json` is generated (the root is
`--tests-root`, default `samples`), and its content has been confirmed by a person in S3.

> `--accept` is the **only way to write a snapshot**; `up2 trial` never writes one automatically, which avoids "recording a wrong product as the right one because it ran once". The command name in the earlier draft had no `--domain` / `--key`, and the case cannot be placed without them: the layout is keyed by the business identity (`05` §3).

**A story that fetches is answered from the request cache** (`uniparser2.net`): the runner replays the
cached answers, so a live site can be frozen and regressed **offline**. A request with no cached
answer is a **miss** — the runner reports it and stops, because **the CLI never reaches the network**:
a host fetches, the runner replays. The cache lives under `.cache/requests/` and is never committed.

### S5 · Regression

```bash
up2 test <domain> <tpl_key>          # every sample of that key against the chain in the Store
up2 test <domain> <tpl_key> --case <case>   # or just one
uv run pytest tests/snapshots -q     # the in-project snapshot cases (05 §4)
```

**Acceptance**: all green. On failure, a **structured difference** is printed (JSON Pointer + expected value + actual value), not a string diff — and `publish` refuses the same way (G2 of §6). A story that fetches gets `fetch` from the request cache; any other host function needs a host, and the runner says so instead of guessing (`03` §4.2).

### S6 · Publish

```bash
up2 publish chain.json --domain ah.gov.cn --key \u653f\u5e9c\u6587\u4ef6\u5217\u8868 --actor llm:claude --source agent
```

**Acceptance**: it prints `PublishResult{chain_id, changed: true, new_hash}`; `up2 get` reads the chain back with a matching fingerprint. It runs G2 first, so a red snapshot is refused unless `--skip-tests --note` says why.

### S7 · Review and rollback

```bash
up2 audit <domain> <tpl_key>                 # the fingerprint chain: who changed what, and when
up2 get <domain> <tpl_key> --graph > backup.json   # backup (rollback material) -- the chain data only
up2 publish backup.json --domain … --key … --actor ops:me --source human --note "roll back to <hash>"
up2 doctor [--fix]                           # chains and audit correspond? --fix writes the missing row
```

> `--graph` is the flag the implementation settled on: the plain `up2 get` prints the stored row
> together with its fingerprint (the S6 acceptance above), and only the graph is publishable again.
> `up2 doctor` is where §10's consistency check-up lives; `--fix` repairs "a chain without an audit
> row" and leaves "an audit row without a chain" as a finding, because there is no chain to write.
> The walkthrough of S0–S7 is executable as written from S2 on.

**Rollback introduces no special mechanism**: audit rows hold only fingerprints, so rollback relies on **an external backup + publishing once more** (the trade-off of draft `01` Q18). Hence the backup action of S7 must appear explicitly in the SOP.

### 7.1 Failure handling table

| Step | Failure symptom | Handling |
|---|---|---|
| S2 | a compile error (`UP2-E1xxx`) | fix the chain per `fix`; the lint rules **must not** be changed or skipped |
| S3 | `Failed` (`UP2-E2xxx`) | the diagnostic names the stage it failed at (its JSON Pointer) and the `fix`; usually a type mismatch or an unreadable path; `up2 trial --trace` names the step, the field and the stage that failed and carries its `code` / `reason` as data (`06` §5.1) |
| S3 | too many empty fields | check whether the field chain that carries the `each` stage produced the elements you thought, and whether the selectors match the current page version; a no-match is the shape's empty value, and `--trace` shows the stage that produced it and the `item` it belongs to |
| S5 | a snapshot difference | first decide whether "the chain regressed" or "the page changed"; the latter needs updated samples, a fresh `--accept`, and a statement of that in the audit `note` |
| S6 | `UP2-E3002` | the `tpl_key` character set is illegal |
| S6 | `UP2-E3003` | chain and audit are inconsistent (leftovers of a file-Store crash) → `up2 doctor --fix` |

## 8. An LLM-friendly interface design

| Design | Content |
|---|---|
| **Capability self-description** | `up2 ops --json` prints, for every operator: name, alias, arity (`arity`) and slot roles (`action_slot` / `slots`), the enumeration of legal actions, the argument schema (including kind), whether the dependency is available, and the install command for a missing dependency. An LLM reads it before drafting and **does not write action names from memory** |
| **Deterministic error codes** | every diagnostic carries `UP2-E<section><number>`; the code tables are in `02` §7 (compile time), `02` §7.1 (runtime) and §5.1 of this file (storage); **the same cause gets the same code**, so an LLM can write "error → fix" as a fixed mapping |
| **Fix hints** | every diagnostic carries `fix` (one sentence) and `allowed` (the list of allowed values), so an LLM need not infer "which options exist" |
| **Structured output** | `lint` / `trial` / `publish` / `get` / `audit` / `test` / `doctor` all support `--json`, and `test` reports each failure as `{pointer, reason, expected, actual}`, so an LLM reads a difference as data. `trial --trace --json` adds the run's per-stage trace to the same document (`06` §5.1): one event per evaluated stage, with the compiled parameters, the input / output views and the failing stage's code and reason |
| **A single source of truth** | the chain JSON is the only source of truth; every step of the SOP only reads or writes that file or the Store, so there is no "hidden state inside an editor" |
| **Reproducibility** | the chain path has no IO (`N1`); the same sample input always yields the same product, which makes snapshot comparison possible |

## 9. Counter-example list (frequent LLM mistakes → error code → fix)

| # | Counter-example | Code | Fix |
|---|---|---|---|
| 1 | comma-packed arguments: `["py","replace","\u65e7,\u65b0"]` | usually a silently wrong value | use a positional array `["py","replace",["\u65e7","\u65b0"]]` |
| 2 | an unescaped literal starting with `$`: `"price": "$100"` | `UP2-E1006` | write `{"$lit": "$100"}` |
| 3 | referencing a node product with `$` (`$rows.url`) | `UP2-E1006` | a node's product is the value its call returns; read `$locals` (every field map writes there) |
| 4 | reading an `each` element's `_` local from another element | `UP2-E2001` | a local belongs to its scope; keep the value in `$public` or in the element's product |
| 5 | `ctx.set` writing `globals.x` | `UP2-E1015` | the write surface is limited to `locals.*` and `public.*` |
| 6 | a misspelt value mode (css: `["css","innerHTML","div.c"]`; xpath: `["xpath","innerText","//item"]`) | `UP2-E1002` | use `["css","html","div.c"]` / `["xpath","text","//item"]` (slot 2 = mode, slot 3 = selector); read `up2 ops --json` first |
| 7 | a bundle with no `nodes` | `UP2-E1005` | declare the callable nodes: `{"nodes": {"parse": [...]}}` (`03` §2) |
| 8 | forgetting the `each` stage, so the fields run once over the whole page (or `each` receives something that is not a list) | the list version fails loudly with `UP2-E2002`; the "ran once over the page" version is a wrong product at runtime | only S3's `trace` can reveal the latter; the `tpl_key` name and the samples should hint that this is a list page |
| 9 | `["py","int",""]` (a parameter written for a function that has none) | `UP2-E1004` | a parameter slot is omitted, never written empty: `["py","int"]`; a time string is parsed with `["py","strptime","%Y-%m-%d"]` and rendered with `py.strftime` |
| 10 | `["re","search",["<pattern>",1]]` with a group the pattern does not have | `UP2-E1005` | check the group index or name against the pattern; `search` takes `[pattern, group]` |
| 11 | putting a node handle straight into the product (forgetting `text`/`@attr`) | `UP2-E2003` | serialize the `Opaque` handle into text first |
| 12 | a node call that closes a cycle (`a -> b -> a`) | `UP2-E1017` | inline one of the nodes, or run two calls from the host |
| 13 | a node key using a reserved name (`globals`) or duplicated | `UP2-E1009` | change the key |
| 14 | `tpl_key` carrying `:` or `/` | `UP2-E3002` | pick a name inside the character set |
| 15 | parsing an answer object as HTML without reading its body first | `UP2-E2002` | `css` sees the object, not text: start the chain with `["py","getattr","text"]` (`03` §4) |
| 16 | a field chain longer than 32 stages / `each` nested deeper than 3 levels / one field map holding more than 256 fields | `UP2-E1012` | split the chain, spread the nesting over several nodes, or switch to `udf` |
| 17 | an empty field map, or a field name that is empty or contains `.` | `UP2-E1005` | declare at least one field, and name each one so a `$…` path can address it |
| 18 | a string written where a chain is expected (`"url": "$in"`) | `UP2-E1004` | write `[]` for identity, or the stages that read a field of the input (`["py","getitem","url"]`) |

## 10. Audit and rollback

| Capability | How |
|---|---|
| Asking "who changed what" | `up2 audit <domain> <key>` prints the fingerprint chain: `at / actor / source / old_hash → new_hash / note` |
| Asking "did this chain change" | as above, comparing the series of `new_hash`; the no-op of `publish` guarantees "no change produces no row" |
| Rollback | **relies on an external backup** (S7's `up2 get --graph > backup.json`) plus one more `publish`. Audit rows record only fingerprints, so a rollback itself also leaves an audit row |
| Consistency check-up | `up2 doctor`: checks whether `chains` and `audit` correspond one-to-one, whether `tpl_key` is legal, and whether `graph` compiles; `--fix` writes the missing audit rows. **Implemented as a store-layer method** (`inconsistencies()` on both stores, `UP2-E3003` findings: a chain with no audit row at all, and an audit row with no chain) plus the `up2 doctor` command with `--fix` (the `07` §3 acceptance item 3). **Not implemented from this row**: the `tpl_key` re-check and the `graph` recompile — the first can only fail on a hand-edited row the store's own step 1 refuses to write, and the second is what every read path already does (`up2 get`, `publish` step 3) |
| Backup advice | in production, snapshot `UP2_HOME` (or the SQLite file) periodically; this design **ships no built-in backup mechanism** (that is an operations concern) |

## 11. The trust boundary of a chain

A chain is persisted, replayed across machines and generated by an LLM, so "what a chain can do at most" must be decidable **at the data layer**. This design writes the trust
boundary as four layers: **the first three are the three sources of code capability** (bottom-up: chain data → host-registered functions → sandboxed code inside the chain), and
**the fourth is the floor of this boundary** (what the sandbox side never does). Every layer's switch is in the **host's** hands, not in the chain; for operator syntax see
`02` §6.4 / §6.10 / §6.12.

### 11.1 Layer one: a chain is data (zero code capability by default)

A chain is JSON, and `core/` contains no `eval` / `exec` / `__import__` (`N6`). **A default installation (including `uniparser2[all]`) installs
no code-execution capability at all**: a chain can only call operators and actions already declared in the registry. This layer is statically decidable — read the chain and read
the output of `up2 ops` and you can enumerate everything it can do; the 40 allowlisted `py` functions are pure functions that ship with the engine (JSON in, JSON out, no IO) and belong to this layer.

### 11.2 Layer two: `udf` = host-registered functions (the chain holds only a name)

A `udf` stage holds only a **function name** (`["udf", "my_fn", {"strict": true}]`); the function's own source is not in the chain and can only be reviewed and registered
in advance by the host (`register_udf`, or the `entry_points` group `uniparser2.udfs`); an unregistered name raises `UP2-E1010` **at compile time**. Hence **registration is
trust**: that function runs with the host's full authority and can touch files, the network and processes; "what this chain can do" = what this deployment has registered. It brings
two consequences that must be remembered:

- **Its auditable nature is deployment-bound**: the same chain under a different deployment may have a different set of usable functions (the `udf` contract is declared as `("udf", "*")`,
  not as individual function names).
- **What it read away must be answered by auditing the function itself**: `ctx` is a **live scope** injected according to the function signature (`ctx.locals` is writable, `ctx.globals` is
  read-only), and a host function sees whatever it wants — the chain data cannot set limits on its behalf.

### 11.3 Layer three: `code` = optional sandboxed code (absent by default)

`code` puts a small piece of code into the chain, so every one of its restrictions must be **explicit** (for details see `02` §6.12):

| Restriction | Shape |
|---|---|
| **Absent by default** | it exists only in the optional extra `uniparser2[code]` (`pydantic-monty`); if that is not installed, a compile-time `UP2-E1107` plus an install command, and `up2 ops` marks it unavailable; **`uniparser2[all]` does not contain it** — installing everything must not incidentally grant code-execution capability |
| **Language-level sandbox** | measured surface by surface instead of by slogan: `import socket` / `import subprocess`, `compile` and `__import__` **do not exist** (`ModuleNotFoundError` / `NameError`); `open(…)` and `os.getenv(…)` **exist and are blocked** by the Monty runtime defaults (`PermissionError` / "not supported in this environment"); `eval` / `exec` exist as language features and carry no capability; the classic escape chain (`''.__class__.__mro__[1].__subclasses__()`) fails at the language level (`AttributeError`) |
| **JSON only** | only the upstream value and the JSON projection of `ctx` enter the sandbox; handles can neither leave the chain (`UP2-E2003`) nor enter the sandbox, and inside the sandbox `ctx` contains JSON values only, with handles excluded without an error |
| **Limits configured explicitly** | memory, single-execution duration, request timeout and host round-trip budget are each pinned by the host (`uniparser2.ops.code.configure`); passing a limit name inside the chain is merely an unknown argument (compile-time `UP2-E1005`) |
| **Deterministic by default** | frozen clock + fixed time zone + no `sleep` + seeded random, which guarantees that the same chain and the same input replay character for character; when the host explicitly switches back to following the host, that guarantee is given up |
| **The chain is self-visible** | the fact that a chain contains code can be grepped in the frozen artifact (the operator name `code`), so an audit need not go back to the host's code |

> **What this repository pins, and what it leaves to the runtime**: `_os_policy()` of `ops/code.py` sets only the determinism knobs (frozen clock, fixed time zone,
> `sleep: zero`, seeded random) and `_limits()` pins memory / feed duration / host round trips; the **file and environment-variable rejections measured above are Monty's own
> defaults**, not a boundary this repository configures. Treat them as defense-in-depth: if an upstream default changes, re-measure (`02` §6.12 states the measured table)
> before restating the claim. The capability claim that does not depend on those defaults is the structural one — nothing host-side is mounted into the sandbox.

### 11.4 Layer four: three things that are never done

| Never done | Reason |
|---|---|
| **Mounting any host capability into the sandbox** | no external callback is passed in, no directory is mounted, no `os` callback is given, no host object wrapper is used. The only host-side thing callable inside the sandbox is **the engine's own pure functions** (the same source as `py`, JSON in, JSON out, no IO), and each call counts as one host round trip — the section "your own callbacks are the weak point" in the upstream library's threat model therefore has nothing to do with this project |
| **Loading a sandbox snapshot** | the bytes of `load_snapshot` must come from a trusted producer; a corrupted or forged snapshot may execute, panic or terminate the process. This design's usage is "a short piece of code runs to completion" and needs no pause/resume, so that capability is not offered |
| **Finding the worker binary via `PATH`** | the worker binary is decided by **a host-side policy** (`SandboxPolicy.binary_path`, which can pin an explicit path), and chain data cannot influence it; in the resolution order the upstream library ships, `PATH` is only the last-resort fallback and this project does not rely on it — pin it with configuration if it must be fixed |

### 11.5 Boundary statement: a language-level sandbox is not OS-level isolation

The sandbox is **language-level**: it makes "code inside the sandbox gets not one byte of host capability" hold, and on top of that the worker child process is responsible only for crash
isolation; the two combined are where the safety here comes from. It is **not** operating-system-level isolation — this project does not promise to withstand implementation flaws of the
interpreter itself (Monty and its worker binary), nor does it promise isolation from problems in other components of the host process; code inside the sandbox and the host still share the same
machine. When an OS-level boundary is needed, that is the container/virtualisation duty of the deployment side, and it is outside the scope of this design.
